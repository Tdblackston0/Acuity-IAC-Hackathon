# Acuity Bicep Module Standard

## File/Folder structure

### Module folder Structure

```
 📂modules
 ┃ ┣ 📂 <Module Family 1>
 ┃ ┃ ┣ 📂 <Module1>
 ┃ ┃ ┃ ┣ 📂 modules
 ┃ ┃ ┃ ┃ ┣ 📜 diagnosticsettings.bicep
 ┃ ┃ ┃ ┃ ┣ 📜 roleassignments.bicep
 ┃ ┃ ┃ ┃ ┣ 📜 <resource>.bicep
 ┃ ┃ ┃ ┃ ┣ 📜 <subresource>.bicep
 ┃ ┃ ┃ ┃ ┗ 📜 <subresource supporting module>.bicep
 ┃ ┃ ┃ ┣ 📂 test
 ┃ ┃ ┃ ┃ ┣ 📂 e2e
 ┃ ┃ ┃ ┃ ┃ ┣ 📂 <test-scenario1>
 ┃ ┃ ┃ ┃ ┃ ┃  ┣ 📜 main.test.bicep
 ┃ ┃ ┃ ┃ ┃ ┃  ┗ 📜 main.test.ps1
 ┃ ┃ ┃ ┃ ┃ ┣ 📂 <test-scenario2>
 ┃ ┃ ┃ ┃ ┃ ┃  ┣ 📜 main.test.bicep
 ┃ ┃ ┃ ┃ ┃ ┃  ┗ 📜 main.test.ps1
 ┃ ┃ ┃ ┣ 📜 bicepconfig.json
 ┃ ┃ ┃ ┣ 📜 exports.bicep
 ┃ ┃ ┃ ┣ 📜 main.bicep
 ┃ ┃ ┃ ┣ 📜 README.md
 ┃ ┃ ┃ ┗ 📜 version.json
 ┃ ┃ ┗ 📂 <Module2>
 ┃ ┣ 📂 exports
 ┃ ┃  ┗ 📜 global.bicep
 ┃ ┗ 📂 <Module Family 2>
 ┃
 ┣ 📂techdocs
 ┃ ┣ 📂 <Module Family>
 ┃ ┃  ┣ 📂 <Module>
 ┃ ┃  ┃ ┣ 📜 metadata.json
 ┃ ┃  ┃ ┣ 📜 README.<version>.md
 ┃ ┃  ┃ ┗ 📜 README.md
 ┃ ┃  ┗ 📜 README.md
```

Each module has a folder with its name inside its module family folder. Inside the root of the module folder is the following.

The folder structure above represents the latest tooling and structure.

- main.bicep
  - Includes imports of exported types.
  - Parameters should represent the customer facing interface and include any defaults.
  - Calls sub-modules from ```modules``` sub-folder. Should not modify resources outside what this resource it defined.
  - Output should include key properties.
- exports.bicep
  - Includes any User-Defined types specific to the module and sub-modules.
- ```modules``` folder
  - Includes core resource module.
  - Includes diagnostic settings module specific to the core resource if supported.
  - Includes role assignments module specific to the core resource if supported.
  - Includes sub-resource modules if needed.
  - Includes sub-resource role and diagnostic settings modules if needed.
- ```test\e2e\<test-scenario>```
  - main.test.bicep
    - Defines an test case for deployment or update.
    - The module in the test case if named 'testDeployment' will produce a example case in the README.md with that includes example bicepparam and json files. Any other name will create an example case.
  - main.test.ps1
    - Runs the test defines by main.test.bicep. Can be actual deployment or a WhatIf.
- README.md
  - Generated by the "Set-ModuleReadMe" command in ```Set-ModuleReadMe.ps1```
  
  ```posh
      $templatePath = (Get-ChildItem .\modules\<Module Family>\<Module>\main.bicep).FullName
      . .\scripts\Set-ModuleReadMe.ps1
      Set-ModuleReadMe -TemplateFilePath $templatePath
  ```

## Module Standards

- All modules should have Role Assignments and Diagnostic Settings if the resource supports them.
- Modules should leverage User Defined Types in the **/modules/exports/global.bicep** where possible.
- If a type a module needs already exists in **global.bicep**, import it from there rather than redefining it. Only define types in the module's **exports.bicep** that are specific to that module.
- When importing types from an a global export explicilit declare the types.

  ```bicep
  import {roleParams} from '../../exports/global.bicep'
  ```

- When importing more than 4 or more types from a module specific export file, user a prefix when importing.

  ```bicep
  import * as kvTypes from 'exports.bicep'
  ```

- User-Defined Types should mark properties with ```?``` at the end of the type if they are optional.
- Do not repeat the parent resource name as a member of a User-Defined Type used for a child collection. The parent name comes from the top-level parameter, so a member of the same name is ignored by the module and forces callers to supply a redundant value.
- Name parameters should declare ```@minLength``` and ```@maxLength``` matching the Azure limits for that resource, so invalid names fail at compile time rather than mid-deployment.
- Do not use the null-forgiving operator (```!```) on optional parameters that are legitimately null for the scenario being deployed. Pass the optional value through and let the API omit it.
- ```union()``` resolves right-to-left: the last object wins. When merging caller-supplied settings with module defaults, put the defaults first so caller values take precedence.
- When calling a sub-module make sure you are passing every parameter of the sub-module.
- When defining sub-modules providing default parameter values is sometimes required to ensure proper processing.
- Where a sub-module resolves its parent with ```existing```, pass the parent's symbolic property (for example ```trafficManager.name```) rather than the raw name parameter. Bicep then infers the dependency and no explicit ```dependsOn``` is needed. Use ```dependsOn``` only where no symbolic reference is passed.
- Deployment names in loops must be unique across the whole file. Prefix them with the resource or module context so two different loops cannot collide.

  ```bicep
  name: '${trafficManagerName}-azure-${endpoint.name}'
  ```

### Outputs

- ```main.bicep``` must output at minimum the resource ID and the resource name, plus any property a consumer would otherwise have to reconstruct by hand (endpoints, FQDNs, IP addresses).
- A module with no outputs cannot be chained into another module and should not be published.
- Never output secrets, keys, or connection strings.

### Resource API Versions

- Prefer the latest GA API version for a resource type.
- A ```-preview``` version is acceptable where it is the newest available for the resource type, or where it is the only version exposing a property the module needs. Several resource types used across this repo (```Microsoft.Authorization/roleAssignments```, ```Microsoft.Insights/diagnosticSettings```) have no newer GA option.
- Within a single module, all files must use the same API version for the same resource type. Mixed versions across ```main.bicep``` and its sub-modules put the parent and its children on different contracts.

### Testing

- Test parameters should be typed against the module's exported User-Defined Types, not a bare ```array``` or ```object```. An untyped test parameter bypasses the type contract, so the test cannot catch a break in it.
- Add a scenario for each distinct code path the module exposes. A sub-module with no test scenario is a sub-module whose bugs will not be found before publication.
- ```main.test.ps1``` must fail the run when the deployment fails. Do not swallow exceptions in a ```catch``` that only writes output.
- Test files must not contain real subscription IDs, tenant IDs, or personal resource names. Parameterize them or deploy a throwaway target within the test.

- When using parameter for nested sub-modules use of User-Defined types to manage the parameters is encouraged for complex types. But the final modulecall in the chain should be an expanded parameters.

  ```bicep
  @description('Optional. Audit settings for this database.')
  param auditSettings databaseAuditSettings?
  //
  //...
  //
  module dbauditSettings 'databaseauditsettings.bicep' = if (!empty(auditSettings)) {
    name: 'auditSettings-${name}'
    params: {
      serverName: serverName
      databaseName: name
      auditActionsAndGroups: auditSettings.?auditActionsAndGroups
      isAzureMonitorTargetEnabled: auditSettings.?isAzureMonitorTargetEnabled
      isManagedIdentityInUse: auditSettings.?isManagedIdentityInUse
      isStorageSecondaryKeyInUse: auditSettings.?isStorageSecondaryKeyInUse
      storageAccountResourceId: auditSettings.?storageAccountResourceId
      queueDelayMs: auditSettings.?queueDelayMs ?? 1000  
      retentionDays: auditSettings.?retentionDays
      storageEndpoint: auditSettings.?storageEndpoint 
      state: auditSettings!.state
    }
    dependsOn: [
      sqlDbs
    ]
  }
  ```

Modules should be tested in personal or Dev subscriptions and WhatIf test against deployed resources before creating a PR.
